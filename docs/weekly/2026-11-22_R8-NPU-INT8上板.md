## 本周目标（≤3 个）
1. ☑ 人工获取 AMCT 包 → WSL modelslim PTQ（S3 策略）产 INT8 ONNX → ATC 离线编 OM → 上传板端跑通。
2. ☑ 板端双口径评估：纯推理延时基准（FP32 vs INT8）+ DMD 16 帧精度对照（输出 cosine / 检出 / person conf / 匹配 IoU，同 R5 口径）。
3. ☑ 精度退化定位：逐层中间特征对照找退化层 → 假设验证 → 修复尝试（v3~v7 共 5 版图），结论如实归档。

## 背景
- 承 R6 周志：NPU INT8 上板因 AMCT 包不可得顺延至本缓冲周；R5 只完成了 CPU 口径（INT8 反而慢 1.3×，量化收益是硬件属性），板端口径收益未验证。
- 承 R4 结论「310B 上 yolov8n 访存/搬运 bound」——INT8 的 I/O 减半对搬运 bound 的模型收益预期可观。

## 核心数据一：纯推理延时（200 iters，bench_latency_acl 同口径）

| 口径 | compute ms | h2d ms | d2h ms | 推理合计 ms | fps |
|------|---:|---:|---:|---:|---:|
| FP32 OM | 12.89 | 1.58 | 1.60 | 16.07 | 62.2 |
| INT8 OM (modelslim v2) | **10.82** | **0.75** | **1.19** | **12.76** | **78.4** |
| INT8 OM (AMCT 0.11.1) | 11.50 | 0.86 | 1.53 | 13.89 | 72.0 |

- compute **↓16.1%**（modelslim）/ **↓10.8%**（AMCT）、推理合计 **↓20.6%** / **↓13.5%**、fps 62.2→78.4 / 62.2→72.0；h2d ↓52%（int8 输入 4.9MB→2.5MB 直接减半）。
- **量化延时收益在 NPU 口径坐实**（R5 CPU 口径「INT8 反而慢」的悬念闭合：收益确实是硬件属性）。
- AMCT 路线 compute 略高于 modelslim（11.50 vs 10.82）：IFMR 标定的 scale 更保守（保留更多动态范围），融合边界处部分层未走纯 int8 快路径——用 ~6% 延时换精度达标（见核心数据二），权衡合理。

## 诊断证据链（四重排除，全部实证）

1. **单层 ATC 链正确**：mini_s7（真实参数单层 q→conv→deq）板端 vs CPU 精确手算 **cos=0.999987**；vs FP32 同层 0.999721 → 单层 int8 链编译执行无误。
2. **图语义正确**：CPU 两层链精确模拟（s7→SiLU→s8_cv1，真实权重/scale）——v2 语义（无输出重量化）cosine **0.99929** ≈ QDQ 语义（有输出重量化）**0.99910** → 「modelslim 丢弃 y_scale 致误差累积」的假说**不成立**，输出重量化修复方向被证伪。
3. **量化策略正确**：CPU QDQ 0.9986 vs 板端 0.9716（同策略）→ 退化非量化本身。
4. **退化模式**：误差非单调累积（s15 回升 0.987），在 s7（stride=2 下采样）与 s8 bottleneck 处跳升 → 指向完整图编译后的执行特性（融合边界精度转换），非逐层均匀漂移。

## 修复尝试与 310B 硬件限制墙（v3~v7 五版图全记录）

| 版本 | 方案 | 结果 |
|------|------|------|
| v3 | 独立 AscendDequant（标量/广播 scale） | ATC 编译失败：`pragma_deq_scale` 仅支持 fp16 输出（mini_f1/f2 证实，与 scale 形状无关） |
| v4 | Mul+Round+Mul 纯 fp32 链模拟重量化 | 编译通过，板端精度**更差**——mini_f5 实测证实 310B 上 fp32 逐元素算子（Mul/Round）**以 fp16 执行**，t=y_fp/sy 大数值下 fp16 ulp 0.5~1 格污染 round 前值 |
| v6 | AscendQuant(int8)+Cast(int8→fp32)+Mul(y_scale) | 数学最优（fp16 ulp 仅 ~0.12 格）但板端**完全崩坏**：int8 张量 trans_data 布局转换在 310B 上结果错乱（mini_f4 编译期 forkserver 崩溃同源） |
| v7 | AscendQuant(dst_type=1，输出 fp32)+Mul | 编译失败：GE InferShapePass `/model.22/Add_1` 报错 |
| v5（最终产物） | 输出重量化链（含 Cast int8→int32 迂回） | 因上述硬件限制未能产出可用 OM（full/mid 编译均失败或非预期） |

- **结论**：v2 的「每层输出截断缺失」在 CPU 数学上并不显著（证据链 2），真实退化源在完整图编译执行侧；而 310B 对独立 quant/dequant/fp32 逐元素算子的四重限制（fp16 强制 / trans_data bug / pragma 限制 / InferShape 失败）封死了软件侧全部修复路径。

### 环境四连坑（全部实证绕过）
| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | custom op 是硬依赖 | calibration 插入 `amct.customop` domain 算子（IFMR/SearchN/Dump）后用 ORT 跑标定，无 op 库则 `InvalidGraph: No opset import for domain 'amct.customop'` | 必须编译 `amct_onnx_op`（「主流程不依赖 custom op」的假设被推翻） |
| 2 | ORT 版本墙 | `SUPPORT_ORT_VERSION = ['1.5.2','1.6.0','1.8.0']`，WSL 主环境 ORT 1.23.2 会被 setup.py 拒绝；且 1.6.0 无 cp39/cp310 wheel | miniconda（TUNA 镜像）建独立 **py3.9** 环境：ORT 1.8.0 + protobuf 3.20.3 + numpy 1.26.4（<2，ORT 1.8 由 numpy 1.x 编译）+ onnx 1.12.0 |
| 3 | GitHub raw 不可达 | custom op 头文件默认从 `raw.githubusercontent.com` 下载（WSL 网络不通，Windows 侧无代理端口，deadsnakes PPA 503，gitee 镜像无老 tag，PyPI 无 sdist，npm onnxruntime-node 是 stub） | 读 `download_inc_files.py` 发现**「inc/ 已存在则跳过下载」**逻辑 → 走 **jsdelivr CDN**：`https://cdn.jsdelivr.net/gh/microsoft/onnxruntime@v1.8.0/include/onnxruntime/core/session/<4 个头文件>`（HTTP 200，`ORT_API_VERSION 8` 精确匹配） |
| 4 | protobuf 冲突 | amct_onnx 的 `_pb2.py` 为老 protoc 生成，新 protobuf 报 `Descriptors cannot be created directly` | py3.9 环境直接降级 `protobuf<4`（3.20.3）；py3.10 主环境可用 `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` 绕过 |

- 编译：`python setup.py build`（g++ 11，14 个 cpp，`-DUSE_C3_ENGINE -std=c++11 -fopenmp`，链接 amct 自带 `libquant_onnx`）→ `libamct_onnx_ops.so`（4.0MB）装入 `amct_onnx/custom_op/`。

### 标定与编译
- 标定集：与 R5/R6/modelslim 路线**完全同源同口径**（12 张 DMD2 帧，letterbox 640，NCHW float32 raw bin）。
- `amct_onnx calibration`（默认配置）：Optimizer 链（ConvBnFusion→DMQBalancer→WeightsCalibration→InsertActCalibration）→ ORT+custom op 跑 12 batch（**9 秒**）→ InsertQuant/Dequant→QuantFusion→WeightQuant→BiasQuant→GenFusionJson→UpdateAscendOp。
- 产物三件套：`yolov8n_amct_default_deploy_model.onnx`（3.3MB，部署用）+ `_fake_quant_model.onnx`（13MB，精度仿真）+ `_quant.json`（187KB，量化参数/融合信息）。
- **ATC 7.0.1 编译 deploy_model → `yolov8n_amct_int8.om`（4.5MB，Ascend310B3）一次通过**——ATC 认 AMCT 产物（对照：onnxruntime 标准 QDQ 被拒 `No parser is registered for Op QuantizeLinear/DequantizeLinear`；modelslim 的 AscendQuant/AscendDequant 可编但板端精度崩）。

### 为什么 IFMR 标定能修复（机制推断）
- 证据链 4 已定位 modelslim 退化在「完整图编译执行的融合边界精度转换」：Percentile 统计标定的 scale 只保证单层张量分布覆盖，**不感知融合后执行精度（fp16 中间存储）引入的二次误差**；深层 bottleneck（s8_m0_cv2，cosine 0.84）处 int8→fp16→int8 的反复转换误差被放大。
- AMCT 0.11.1 的 **IFMR（迭代流最小重建）+ DMQ Balancer**：逐层迭代搜索使「量化-反量化重建误差」最小的 scale，且标定过程本身在 ORT 里带 custom op 精确模拟量化行为——scale 对融合边界的精度转换天然更鲁棒。
- 延时侧代价：IFMR scale 更保守 → 部分层未走纯 int8 快路径 → compute 11.50 vs 10.82ms（+6%），换取精度从「不可用」到「几乎无损」。

## 遇到阻碍 / 遗留问题
- **已闭合（11.25 晚）**：NPU INT8 上板精度问题——modelslim 路线不达标（cosine 0.9716 / IoU 0.0）且软件修复被 310B 硬件限制墙封死；**AMCT 0.11.1/IFMR 路线达标**（cosine 0.99871 / IoU 0.973 / 检出数与 FP32 完全一致），R5 遗留「真·NPU INT8 OM 上板」正式闭环。
- **仍开放（非阻塞）**：modelslim 路线在 310B 上深层融合边界精度转换的精确机制（fp16 中间存储 × Percentile scale 的交互）未完全白盒化，留 R10 报告作「已知限制 + 双路线对比」章节；AMCT 路线延时比 modelslim 高 ~6% compute，若追求极限延时可再做 IFMR 配置调优（record 粒度 / 部分层 fp16 回退）。
- **工具链边界更新**：CANN 7.0.1 自带 modelslim ≠ 完整 AMCT——老版 AMCT 0.11.1 独立包（社区 OBS 直链可匿名取）的 IFMR 标定在 310B 上精度鲁棒性显著更好；「ATC 拒绝 QDQ」的准确表述是：拒绝 onnxruntime 标准 QDQ，接受 modelslim 的 AscendQuant/Dequant 与 AMCT deploy_model 两种私有表示。
