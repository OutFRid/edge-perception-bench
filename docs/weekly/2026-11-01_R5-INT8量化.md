# R5 · 主题：INT8 量化——精度损失 vs 延时收益

> 日期区间：2026-11-01 ~ 2026-11-07
> 状态：🔄 进行中（量化链路 + 精度损失 + 通用 CPU 延时口径已完成；**NPU 侧 INT8 延时收益受工具链阻塞，转 R6/缓冲周**）

## 背景
- 日历 R5 技术任务：**INT8 量化：FP32→INT8，记录精度损失 vs 延时收益**。
- 承接 R4：310B 上 yolov8n 是 **访存/搬运 bound**（算力仅 3.5ms，搬数 5.7ms）。故带着问题进场——「INT8 的延时收益到底发生在哪一层？」

## 本周目标（≤3 个）
1. ☑ 产出真正的 INT8 量化模型（FP32→INT8），并做体积/结构核对。
2. ☑ 量化 **精度损失** 实测：FP32 vs INT8 在同批真实图片上的输出保真度与检测级一致性。
3. 🔄 量化 **延时收益** 实测：通用 x86 CPU 口径已测；**昇腾 NPU 侧 INT8 OM 未能编译上板**（见阻碍）。

## 量化方法（可复现）
- 环境：WSL Ubuntu-22.04（torch 2.14 / ultralytics 8.4 / onnx 1.23），新装 `onnxruntime 1.23.2`。
- 链路：`scripts/wsl_quant_yolo.py`
  1. ultralytics 以 **opset=13** 重导 `yolov8n_fp32.onnx`（QDQ per-channel 需 opset≥13）；
  2. 用 12 张真实图片做标定，`onnxruntime.quantization.quantize_static`（**QuantFormat.QDQ / per-channel / QInt8 权重&激活 / MinMax**）→ `yolov8n_int8.onnx`；
  3. onnxruntime CPU 各跑一张做量化自检。
- 评估：`scripts/wsl_r5_quant_eval.py`（16 张真实图片，单线程 CPU）。
- 产物：`models/yolov8n_int8.onnx`、`results/doc/r5_int8_eval.json`、`results/doc/r5_quant_selfcheck.json`。

## 本周实际产出（核心数据）

### ① 量化模型
| 指标 | FP32 | INT8 (QDQ) |
|---|---:|---:|
| ONNX 体积 | 12.2 MB | **3.4 MB（↓3.6×）** |
| 权重位宽 | float32 | int8（per-channel） |

### ② 精度损失（16 张真实图片，FP32 vs INT8）
| 口径 | 结果 | 解读 |
|---|---|---|
| 原始输出 cosine（均值/最小） | **0.99875 / 0.99746** | 输出张量高度保真 |
| 检出框数 / 图（FP32→INT8） | 0.94 → 1.12 | 近乎持平（INT8 略多候选） |
| person 平均置信度 | 0.7104 → 0.6890 | **降 0.021**（~3% 相对） |
| 匹配框 IoU（均值/最小） | **0.895 / 0.0** | 多数框位置高度一致；min=0 来自 INT8 多出的个别候选 |

> **结论：本任务上 INT8 PTQ 近乎无损**——置信度仅掉 0.02、框位 IoU 0.895，检测语义保持。（注：样本为通用图非 DMD 专集，属"合理性代理"而非 mAP；上板 mAP 待 NPU INT8 打通后补。）

### ③ 延时收益（通用 x86 CPU，单线程 onnxruntime，30 iters）
| 模型 | mean | p95 |
|---|---:|---:|
| FP32 | **74.2 ms** | 75.7 |
| INT8 | **96.4 ms** | 98.2 |

> **反直觉但重要的发现：INT8 在通用 CPU 上反而慢 1.3×**。原因：onnxruntime CPU 的 QDQ INT8 路径缺乏 x86 融合 int8 kernel（VNNI 未命中），量化/反量化节点的开销 > int8 算力收益。**量化收益强依赖硬件是否有 int8 MAC 单元**——这正是需要 NPU 的场景。

## 三条认知
1. **量化收益不是"免费的"，它是硬件属性**：同一份 INT8 模型，在有 int8 定点单元的 NPU/DSP 上才可能转化为延时/功耗收益；在通用 CPU 上可能净亏。R4 已证 NPU 侧算力只占 3.5ms，所以 **INT8 对本项目 E2E 的真实收益预计有限且主要来自体积/带宽**——需上板坐实。
2. **精度损失要分口径报**：置信度、检出数、框位 IoU、原始张量 cosine 是不同层级；只报 cosine 会把"框跑偏"藏起来。
3. **ATC 不认通用 ONNX 的 QDQ**：昇腾离线 INT8 走的是 **AMCT（配套量化）** 而非"任意 QDQ ONNX 直接编"。工具链假设要先验证再排期（本周就是在验证处碰壁）。

## 遇到阻碍 / 遗留（NPU INT8 上板为何受阻）
- **ATC 拒绝通用 QDQ ONNX**：`atc` 报 `No parser is registered for Op [...::QuantizeLinear/DequantizeLinear]` → `Model parse to graph failed`。CANN 7.0.RC1 的 ONNX parser 不解析标准 QDQ 节点。
- **缺离线量化器**：板端/WSL toolkit 仅有 `amct` **运行库头**与 `amct_inner_graph_build`，**无 `amct`/`msct` 离线量化 CLI**（AMCT 是需按 CANN 版本单独下载、绑定训练框架 + 专用标定集的独立工具包）。
- 结论：**真·NPU INT8 OM 本周无法产出**，不上板就不编 NPU INT8 延时/上板 mAP。→ 记为 R6/缓冲周任务：装配套 AMCT（或走昇腾 "量化" 官方样例链），把同一份标定/评测口径复用到 OM 上，补齐「NPU INT8 延时收益 + 上板精度」。
- 诚实标注：**没有把"没上板的 NPU INT8"粉饰成已达标**——本周交付的是量化模型、精度损失实测、以及"收益依赖硬件"这一被 CPU 数据敲实的认知。
